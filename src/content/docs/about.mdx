## Documentation & Architecture Philosophy

I am a software engineer and technical writer. My philosophy is simple: **write for the reader, not the writer.** 

Every piece of documentation, runbook, and architectural specification I create starts with three critical questions:
1. **Who** will read this (`Developer`, `Support Engineer`, `Architect`, `Content Editor`, or `AI Agent`)?
2. **What** is their exact technical proficiency and context?
3. **What** concrete task must they accomplish immediately after reading it?

Good technical documentation should reduce cognitive load, provide clear paths to success, and anticipate exact production bottlenecks. Whether writing OpenAPI schemas for developers, SOP debugging runbooks for support engineers, high-level architecture designs for product leads, or machine-readable context for AI coding agents, clarity and precision are the core of my approach.

## Technical Knowledge Hubs

To structure complex engineering documentation across diverse domains, this knowledge base is organized into three primary engineering hubs:

- **🎯 Developer Docs & API (Offline):** Technical specifications, OAuth 2.0 sequence flows, JSON request/response schemas, and AWS EC2 onboarding tutorials for software engineers, API integrators, and developer enablement.
- **🎯 Troubleshooting & Runbooks (Offline):** Actionable Standard Operating Procedures (`Symptom → Diagnosis → Fix`), Canvas LMS integration error resolutions, distributed log tracing, and local SSL bypass runbooks (`thisisunsafe`) for support engineers, SREs, and operations teams.
- **🎯 Architecture & Project Logic (Offline):** High-level system decomposition, Canvas LMS + AWS infrastructure diagrams, mathematical algorithm modeling (`KaTeX`), and trade-off analysis across live production deployments for system architects, engineering leads, and technical managers.

## Documentation Methodology

<CardGrid>
  <Card title="Diátaxis Framework" icon="puzzle">
    Every page in this knowledge base is structured according to the [Diátaxis framework](https://diataxis.fr/) — a systematic approach to documentation authoring that classifies content into **Tutorials**, **How-to Guides**, **Reference**, and **Explanation** based on user needs. This ensures each document has a clear purpose and appropriate tone for its audience.
  </Card>
  <Card title="Prose Linting with Vale" icon="approve-check">
    All documentation is linted with [Vale.sh](https://vale.sh/) using the [Google Developer Documentation Style Guide](https://developers.google.com/style) and [Microsoft Writing Style Guide](https://learn.microsoft.com/en-us/style-guide/developer-content/) as baselines. This enforces consistent tone, terminology, and clarity across every page — the same tooling used by AWS, NVIDIA, GitLab, and Docker.
  </Card>
</CardGrid>
