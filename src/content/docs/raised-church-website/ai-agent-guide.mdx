## SYSTEM_CONTEXT

You are an expert AI software engineer operating within the Raised Church Website repository. 
- **Framework**: SvelteKit (App Router, Server-Side Rendering)
- **Language**: TypeScript (Strict mode enabled)
- **Styling**: Tailwind CSS
- **CMS**: Contentful (Headless REST API)
- **Deployment**: Vercel
- **Primary Goal**: Maintain a fast, accessible, bilingual (en/zh) church website.

## DIRECTORY_STRUCTURE

```text
src/
  ├── app.d.ts           # Global TS definitions
  ├── app.html           # Main HTML template
  ├── lib/               # Internal library
  │   ├── components/    # Reusable Svelte components (UI only, no data fetching)
  │   ├── server/        # Server-only code (Contentful SDK, secret keys)

  └── routes/            # SvelteKit filesystem routing
```

## CODING_CONVENTIONS

### 1. Data Fetching (STRICT RULE)
- **DO NOT** fetch data from Contentful in `+page.svelte` or `+page.ts`.
- **ALWAYS** fetch data in `+page.server.ts` using the server-side Contentful client.
- Expose data to the component via the `data` prop.
- **Reason**: Protects Contentful API keys; ensures SEO-friendly SSR.

### 2. Svelte Component Patterns
- Use `<script lang="ts">` for all Svelte components.
- Avoid inline styles. Use Tailwind CSS utility classes exclusively.
- Extract complex logic outside of the `.svelte` file into `.ts` utilities in `src/lib/`.
- Use Svelte 4 reactivity syntax (`$:` for reactive statements). Do not use Svelte 5 runes (`$state`) as this project is currently on Svelte 4.

### 3. Bilingual Support (i18n)
- For CMS content: Pass the current locale from `event.locals.locale` to the Contentful API query.
- For static UI text (e.g., "Read More", "Submit"): Use the custom i18n store imported from `$lib/i18n`. 
- **DO NOT** hardcode English or Chinese strings directly in `.svelte` templates.

### 4. Contentful Integration
- Use the official `contentful` npm package.
- Type definitions for Contentful entries are located in `src/lib/types/contentful.d.ts`. Always cast CMS responses to these types.
- Handle rich text rendering using `@contentful/rich-text-html-renderer`.

## COMMON_TASKS_AND_PATTERNS

### Task: Adding a New Route
1. Create a new directory in `src/routes/`, e.g., `src/routes/ministries/`.
2. Create `+page.server.ts` for data requirements.
3. Create `+page.svelte` for the UI.
4. If it requires a dynamic slug, use bracket notation: `src/routes/ministries/[slug]/`.

### Task: Modifying Content Types
If you are instructed to handle a new field added to Contentful (e.g., adding a `subheading` to the `Sermon` content type):
1. Update the TypeScript interface in `src/lib/types/contentful.d.ts`.
2. Ensure the GraphQL/REST query in `+page.server.ts` retrieves the new field.
3. Update the corresponding `+page.svelte` to render the field, ensuring graceful fallbacks if the field is undefined (not all past entries will have the new field).

## ANTI_PATTERNS (DO_NOT_DO_THESE)
- 🚫 Do not import `$lib/server/...` into any `.svelte` file. It will cause build errors.
- 🚫 Do not use `fetch` on the client side to hit Contentful APIs directly.
- 🚫 Do not write raw CSS in `<style>` tags unless absolutely necessary for complex animations that Tailwind cannot handle.
- 🚫 Do not commit `CONTENTFUL_ACCESS_TOKEN` to the repository.

## TESTING_AND_VALIDATION
Before finalizing your output, verify:
1. TypeScript compilation passes (`npm run check`).
2. Tailwind classes used actually exist in Tailwind v3.
3. Both English and Chinese locales have been accounted for in UI changes.
4. Server functions return serializable data (no raw class instances, use POJOs).
