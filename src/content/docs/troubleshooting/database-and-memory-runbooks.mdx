## Full-Stack Operational Scope

Technical Support Engineers must possess diagnostic fluency across both legacy stateful infrastructure and modern serverless cloud deployments. A root-cause investigation might require stepping down into C-level process memory tables on an Apache server in the morning, and debugging GraphQL webhook payloads on a static edge network in the afternoon.

This consolidated operational runbook bridges our engineering experiences across two core portfolio architectures: our legacy stateful academic evaluation platform, [TeamAssign](/teamassign/overview), and our modern serverless Jamstack deployment, the [Raised Church Website](https://raisedchurch.com). Every section provides rigorous triage procedures (`Symptom → Diagnosis → Fix → Prevention`) across database optimization, process lifecycle management, and headless CMS webhook recovery.

## 1. `mod_perl` Memory Leak Isolation (`TeamAssign`)

### Symptom
Over a continuous 48-to-72-hour operating window, monitoring alerts indicate rising memory utilization across the **TeamAssign** production web nodes. Apache 2 worker child processes (`httpd` or `apache2`) steadily expand their Resident Set Size (RSS) memory footprint from an initial 45 MB up to 600+ MB per process. Eventually, the operating system exhausts physical RAM and swap space, triggering the Linux OOM (Out of Memory) Killer (`Out of memory: Kill process...`), which forcibly terminates web workers and causes `502 Bad Gateway` timeouts for end users.

### Diagnosis
Unlike standard CGI or modern ephemeral serverless workers (`AWS Lambda`), `mod_perl 2.0` embeds a persistent Perl interpreter directly inside each Apache worker process. While this eliminates startup compilation overhead and delivers high-performance request handling, it introduces severe memory persistence risks:
1. **Un-Garbage-Collected Package Variables**: Any variable declared at the package level (`our $CACHE = {}` or lexicals `my %SESSION_STORE` defined outside subroutine boundaries) persists across thousands of independent HTTP requests handled by that specific Apache child process.
2. **Circular References in Object ORM Layers**: When two Perl objects reference each other (`$parent->{child} = $child; $child->{parent} = $parent;`), Perl's reference-counting garbage collector cannot decrement the reference counts to zero when the request ends. The allocated memory block is orphaned and leaked permanently into the worker's heap space.
3. **Unreleased DBI Statement Handles**: Failing to explicitly finish database handles (`$sth->finish()`) when terminating early inside conditional loops traps underlying database client buffers within memory.

### Fix (Step-by-Step Resolution)

<Steps>
1. **Isolate Leaking Apache Child Processes (`ps` & `pmap`)**
   Identify the top memory-consuming Apache child PIDs and inspect their underlying memory map allocations on the production VM:
   ```bash
   # List top 10 Apache processes sorted by Resident Set Size (RSS)
   ps aux --sort -rss | grep apache2 | head -n 10

   # Inspect detailed memory segment breakdown for a specific high-memory PID
   sudo pmap -x <target_pid> | tail -n 5
   ```

2. **Audit & Break Circular References using `weaken`**
   Run the codebase through `Devel::Cycle` to detect circular references within custom Model classes. Where circular structures are mandatory (e.g., bi-directional tree traversals), enforce weak references using `Scalar::Util::weaken`:
   ```perl
   package TeamAssign::Model::TeamMember;
   use strict;
   use warnings;
   use Scalar::Util qw(weaken);

   sub set_parent_team {
       my ($self, $team_obj) = @_;
       $self->{parent_team} = $team_obj;
       # CRITICAL: Weaken the reference to allow reference-counting GC to reclaim memory upon request cleanup
       weaken($self->{parent_team});
   }
   ```

3. **Configure Apache Worker Lifecycle (`MaxConnectionsPerChild`)**
   To establish a deterministic bound on process memory growth without dropping active connections, configure Apache's Prefork MPM module to gracefully recycle child workers after serving a finite number of requests:
   ```apache
   # /etc/apache2/mods-enabled/mpm_prefork.conf
   <IfModule mpm_prefork_module>
       StartServers              5
       MinSpareServers           5
       MaxSpareServers          10
       MaxRequestWorkers       150
       # Force worker recycling after 1,000 requests (prevents unbounded leak accumulation)
       MaxConnectionsPerChild 1000
   </IfModule>
   ```
   Apply the configuration changes gracefully:
   ```bash
   sudo apache2ctl graceful
   ```
</Steps>

### Prevention
- **Automated Memory Profiling in CI**: Integrate `Test::Memory::Cycle` into automated unit test suites to fail builds immediately if any new data structure introduces an un-weakened circular reference.
- **Enforce Strict Lexical Scoping**: Prohibit `our` variables for request-level caching; utilize `Apache2::RequestUtil->request->pnotes()` to store transient request data that automatically purges when the HTTP transaction concludes.

## 2. N+1 Database Query Bottlenecks & Optimization

### Symptom
Instructors attempting to export course evaluation summaries or view aggregate peer review reports for large classes (300+ students across 60 teams) experience severe latency. Requests hang for 30+ seconds before either rendering or timing out with `HTTP 504 Gateway Timeout` or database connection pool starvation (`DBI connect failed: Too many connections`).

### Diagnosis
An N+1 query bottleneck occurs when an application fetches a parent dataset ($1$ query) and then iterates through every returned parent record to execute an individual database query ($N$ queries) for child associations.

By enabling the MySQL Slow Query Log (`slow_query_log = 1`), forensic inspection reveals that rendering a single course summary page executes over **1,500 individual SQL requests**:
1. `$1$ query` to select all teams in the course (`SELECT * FROM teams WHERE course_id = 101`).
2. `$50$ queries` to select members for each team inside a loop (`SELECT * FROM team_members WHERE team_id = ?`).
3. `$1,500$ queries` to fetch survey responses for each student inside nested loops (`SELECT * FROM evaluations WHERE evaluatee_id = ?`).

Each query incurs network round-trip latency and database query planning overhead. Even when individual queries execute in $1.5\text{ ms}$, executing $1,551$ queries serially forces the page load time over $23\text{ seconds}$.

### Fix (Step-by-Step Resolution)

<Tabs>
  <TabItem label="Legacy Pattern (N+1 Anti-Pattern)">
    **Do NOT write nested iteration loops** that trigger database queries per object:

    ```perl
    # ANTI-PATTERN: Executes 1 + N + (N * M) queries
    my @teams = $schema->resultset('Team')->search({ course_id => $course_id });

    foreach my $team (@teams) {
        my @members = $team->team_members(); # Executes SQL query per team!
        foreach my $member (@members) {
            my @evals = $member->evaluations(); # Executes SQL query per member!
            # Process evaluation scores...
        }
    }
    ```
  </TabItem>
  <TabItem label="Optimized Eager Loading (`JOIN` Prefetch)">
    Refactor the ORM call (`DBIx::Class` or raw SQL) to execute a single, highly optimized **`LEFT OUTER JOIN`** with eager loading (`prefetch`), consolidating all parent and child data into a single query round-trip:

    ```perl
    # OPTIMIZED: Executes exactly 1 SQL query with JOIN eager loading
    my @teams = $schema->resultset('Team')->search(
        { 'me.course_id' => $course_id },
        {
            prefetch => { 'team_members' => 'evaluations' },
            order_by => [ 'me.name', 'team_members.last_name' ]
        }
    );

    # All nested child objects are pre-populated in memory during the initial query traversal
    foreach my $team (@teams) {
        foreach my $member ($team->team_members()) { # No SQL query fired!
            foreach my $eval ($member->evaluations()) { # No SQL query fired!
                # Process evaluation scores instantaneously from local memory...
            }
        }
    }
    ```
  </TabItem>
  <TabItem label="Raw SQL Execution Plan (`EXPLAIN ANALYZE`)">
    Verify composite index utilization across the join keys (`idx_course_team_user`) using MySQL's query analyzer before deploying to production:

    ```sql
    EXPLAIN ANALYZE
    SELECT t.id, t.name, tm.user_id, e.score, e.comments
    FROM teams t
    LEFT JOIN team_members tm ON t.id = tm.team_id
    LEFT JOIN evaluations e ON tm.user_id = e.evaluatee_id
    WHERE t.course_id = 101;
    ```
    *Target Metric: Execution plan must use `Index Lookup` on composite indexes with total execution time $< 45\text{ ms}$.*
  </TabItem>
</Tabs>

### Prevention
- **Database Query Budget Alerts**: Configure application middleware to log a high-priority warning if any single HTTP request executes more than **15 distinct SQL queries**.
- **Automated Query Plan Auditing**: Require all pull requests modifying reporting endpoints or data exports to attach an `EXPLAIN ANALYZE` execution plan verifying zero full table scans (`ALL`).

## 3. Contentful CMS Webhook Sync Recovery (`Raised Church Website`)

### Symptom
Content editors at the [Raised Church Website](https://raisedchurch.com) publish updates to sermon notes, staff profiles, or event schedules inside the Contentful web studio. However, the live website fails to reflect the updates after the expected 3-minute static site build window.

Inspecting our Vercel production dashboard reveals that the webhook-triggered deployment failed with build errors during the SvelteKit static site generation (`vite build` / `prerender`):

```text
Build Error: TypeError: Cannot read properties of undefined (reading 'fields')
    at formatSermonEntry (/vercel/path0/src/lib/utils/contentful.ts:48:22)
    at prerenderRoute (/vercel/path0/.svelte-kit/output/prerender/pages/sermons.json)
```

### Diagnosis
Our Jamstack architecture (`SvelteKit` + `Contentful GraphQL API` + `Vercel`) relies on Contentful webhooks to trigger static page prerendering whenever content changes. Build failures during webhook synchronization occur due to two structural anomalies:
1. **Unresolved Draft or Deleted Asset References**: An editor published a parent entry (e.g., a `Sermon` record) that references a child asset or author bio that is **still in `Draft` state** or was recently **deleted**. When the SvelteKit build pipeline queries the Contentful Delivery API (which only returns published entries), the referenced relationship returns `null` or `undefined`. Without defensive null checks, the build crashes when accessing `.fields.file.url`.
2. **Schema & Slug Validation Violations**: An editor pasted malformed Markdown containing unescaped HTML characters or generated a URL slug with spaces (`/events/summer camp 2026`), violating our strict TypeScript/Zod build-time validation schemas.

### Fix (Step-by-Step Resolution)

<Steps>
1. **Isolate the Failing Contentful Entry ID via Vercel Logs**
   Retrieve the exact deployment failure logs using the Vercel CLI to identify the entry ID and route that broke static generation:
   ```bash
   vercel logs --prod --limit 50 | grep -C 3 "Build Error"
   # Output identifies broken route (e.g., /sermons/grace-abounds) and entry ID (entry: 6k9Xz4...)
   ```

2. **Inspect Raw Webhook & Preview Payloads via cURL**
   Query the Contentful Preview API directly (`api.preview.contentful.com`) using your internal read-only preview token to inspect the raw JSON structure of the problematic entry and locate the null reference:
   ```bash
   curl -s -X GET "https://api.preview.contentful.com/spaces/YOUR_SPACE_ID/environments/master/entries/6k9Xz4?include=2" \
     -H "Authorization: Bearer YOUR_PREVIEW_TOKEN" | jq '.fields.speaker'
   ```

3. **Execute Local Sync Validation & Recovery**
   Run our local diagnostic sync validation tool from the repository root to verify structural consistency without consuming Vercel build quotas:
   ```bash
   npm run sync:validate -- --entry=6k9Xz4
   ```

4. **Correct Content Store & Trigger Manual Webhook Re-Sync**
   Instruct the content editor to either **publish the draft asset reference** inside Contentful Studio or unlink the broken item. Once corrected, trigger a manual rebuild by dispatching an authenticated POST request directly to the Vercel deploy hook URL:
   ```bash
   curl -X POST "https://api.vercel.com/v1/integrations/deploy/YOUR_VERCEL_WEBHOOK_ID"
   ```
</Steps>

<Aside type="tip">
**Defensive Frontend Rendering Pattern**
Ensure all SvelteKit data loaders and component templates implement strict optional chaining (`entry?.fields?.speaker?.fields?.name ?? 'Guest Speaker'`) and fallback UI skeletons. Never assume third-party CMS references are non-null during static generation.
</Aside>

### Prevention
- **Contentful App Pre-Publish Validation Rules**: Install custom validation scripts within Contentful Studio (`Validation App`) that block editors from publishing any Entry containing un-published (`Draft`) asset references.
- **Preview Environment Verification**: Configure Vercel to run automated preview builds against Contentful's Preview API for all content branches before merging schema changes to `master`.
